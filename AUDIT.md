## Critical

### C-01. Гонка входа по коду даёт доступ к чужой паре

- Файл: `duoplan/services.py:66-82`, зависимость — `duoplan/services.py:44-49`.
- Проверка `pair["user_b"]` и `UPDATE ... WHERE user_b = 0` не образуют транзакцию, а результат `UPDATE` не проверяется.
- Два пользователя могут одновременно ввести один код: оба получают `True`, `pairs.user_b` достаётся последнему, но `users.pair_id` записывается обоим.
- Воспроизведено: **20 из 20** конкурентных запусков дали два успешных входа.
- Последствие: пользователь без фактического членства видит и изменяет планы, дневник и желания пары. Это нарушение приватности.
- Исправление: транзакция `BEGIN IMMEDIATE`, проверка `changes == 1`, условный `UPDATE users ... WHERE pair_id IS NULL`, откат при нулевом результате. Добавить `UNIQUE`-ограничение на занятые `user_a/user_b` там, где это применимо.

### C-02. Владелец пустой пары может вступить в другую пару

- Файл: `duoplan/services.py:66-72`; причина — `pair_for()` требует `user_b != 0` (`duoplan/services.py:44-49`).
- Сценарий: пользователь создал пространство, затем нажал «Ввести другой код» и ввёл код другой пары.
- Проверено на in-memory SQLite: вход разрешён; пользователь остаётся `user_a` первой пары и становится `user_b` второй.
- Последствие: осиротевшая пара, расщепление данных, невозможность понять, где «настоящее» пространство.
- Исправление: проверять `membership()` и `users.pair_id`, а не только заполненную пару. При существующем членстве либо запрещать вход, либо явно выполнять перенос с подтверждением.

### C-03. Python-бот и Cloudflare Mini App несовместимы по транспорту и данным

- Файлы: `duoplan/__main__.py:36`, `worker.js:227-233`, `duoplan/db/base.py:91-94`, `wrangler.jsonc:11-18`.
- Python использует long polling и SQLite `data/duoplan.db`; Worker устанавливает webhook и пишет в D1.
- Одновременный запуск polling и webhook на одном `BOT_TOKEN` приводит к конфликту Telegram (`409`).
- Пары и записи, созданные в одной поверхности, не видны в другой.
- Исправление: объявить D1 единственным источником истины, а Python-бота либо перевести в тонкий клиент API, либо вывести из эксплуатации. Перед переходом сделать одноразовый экспорт SQLite → D1.

## High

### H-01. Двойное начисление XP за ритуал в Python-боте

- Файл: `duoplan/services.py:173-202`, проверки — `175-179`, записи — `189-200`.
- Между чтением `done_by` и обновлением нет транзакции; три записи коммитятся отдельно.
- Проверено: два одновременных вызова дали `points = 10` обоим и `together_pts = 20` вместо 10. Повторено **3 из 3**.
- Дополнительно: сбой между обновлениями оставляет ритуал отмеченным без начисления XP.
- Исправление: один условный `UPDATE ... WHERE done_by IS NULL` с проверкой `changes`, затем начисление в той же транзакции.

### H-02. Медиа в FSM-состоянии роняет обработчик

- Файлы: `duoplan/handlers.py:319-322`, `328-329`, `335-337`, `354-356`, `362-364`; `duoplan/handlers.py:174-176`.
- `StateFilter` не требует текста, но код вызывает `message.text.strip()` или передаёт `None` в сервис.
- Сценарий: фото, стикер, GIF или голосовое во время ввода плана, даты, кода, записи или желания.
- Последствие: `AttributeError`, пользователь не получает ответа и остаётся в зависшем состоянии.
- Исправление: `F.text` в фильтрах, отдельный ответ на не-текст, глобальный error handler, сброс/подсказка для состояния.

### H-03. Часовой пояс загружается, но не применяется

- Файлы: `duoplan/config.py:99-107`; `duoplan/services.py:57,125,158,174,181`; `duoplan/handlers.py:339`; `worker.js:16`.
- Python использует `date.today()` сервера, Worker — UTC через `toISOString()`.
- В Москве сутки переключаются в 03:00, а не в 00:00; даты воспоминаний, ритуал и серия могут относиться к другому дню.
- Исправление: хранить IANA-зону пары/пользователя и вычислять локальную дату; для Python использовать `datetime.now(settings.tz)`. Зафиксировать единое правило для обеих поверхностей.

### H-04. `/api/setup` полностью открыт

- Файлы: `worker.js:215-239`, `worker.js:252`, `public/setup.html:14`.
- Любой может отправить POST без авторизации, пересоздать схему и повторно установить webhook, команды и menu button.
- Возможен перевод webhook на preview-домен, исчерпание лимитов Telegram и CSRF через автоматическую отправку формы.
- Исправление: отдельный setup-секрет в заголовке с constant-time сравнением либо Cloudflare Access; ограничить допустимый host; закрыть `/setup.html` после активации; добавить rate limit.

### H-05. Гонки создания и соединения пары в Worker

- Файлы: `worker.js:60-81`; отсутствие блокировки кнопки — `public/app.js:188`.
- `createPair`: два параллельных запроса видят отсутствие членства и создают две пары.
- `joinPair`: два запроса к разным парам могут оба пройти проверку членства и записать пользователя в обе.
- Последствие: фантомные пары, потерянные данные, партнёр видит не то пространство.
- Исправление: один источник истины для членства, `env.DB.batch()` с проверкой `meta.changes`, условные `UPDATE ... WHERE pair_id IS NULL`, компенсирующий откат, идемпотентный create.

### H-06. Экран загрузки не скрывается

- Файлы: `public/app.css:1` (`.outside{display:flex}`), `public/app.js:220` (`outside.hidden = true`), `public/app.html:38-40`.
- Авторское `display:flex` перебивает пользовательское правило `[hidden]`.
- Последствие: под приложением остаётся второй экран высотой `100vh` с вечным спиннером.
- Исправление: `[hidden]{display:none!important}` или класс `.is-hidden`; тест на видимость всех трёх состояний.

### H-07. Ошибка API закрывает форму, стирает ввод и показывает ложный успех

- Файлы: `public/app.js:140-152`, `154-173`, `197-206`.
- `refresh()` перехватывает ошибку и не сообщает о ней вызывающему коду.
- После неуспешного сохранения диалог всё равно закрывается и `form.reset()` очищает введённые данные.
- После ошибки `done-task`, `done-wish` или `done-daily` всё равно показывается success-toast, а кнопка остаётся disabled.
- Исправление: возвращать результат/пробрасывать ошибку, закрывать и сбрасывать форму только при успехе, success-toast — только после подтверждённого изменения, кнопку разблокировать в `finally`.

### H-08. Вишлист недоступен из навигации

- Файлы: `public/app.html:21-27`, `public/app.js:46`, `184-186`.
- Пятого пункта «Желания» нет; при `route === "wishes"` подсвечивается «Главная».
- Кнопка «+» не предлагает выбор типа, а циклически меняет раздел и открывает форму.
- Последствие: обещанная на лендинге функция фактически спрятана, навигация непредсказуема.
- Исправление: отдельный пункт «Желания» или «Ещё», а «+» должен открывать выбор типа без смены текущего раздела.

### H-09. После ритуала интерфейс показывает старые XP и серию

- Файлы: `worker.js:96-108`, `worker.js:163`, `public/app.js:84`.
- `state()` получает объект `user` до мутации и возвращает его после обновления D1.
- Последствие: личные XP и streak в ответе на `/api/daily/done` устаревшие; `together_pts` при этом новый.
- Исправление: перечитывать пользователя после мутации либо собирать `state` только после завершения записи.

## Улучшения по коду

1. **Один backend.** D1 — единственный источник данных; Python-бот либо вызывает API Worker, либо архивируется. Это устраняет C-03 и рассинхронизацию функций.
2. **Транзакции и ограничения.** Все парные операции — через batch/transaction с проверкой `meta.changes`; добавить ограничения целостности для членства и уникальности активных связей.
3. **Единый слой валидации.** Общие лимиты строк, проверка календарных дат, нормализация кода приглашения, единые сообщения об ошибках для бота и Mini App.
4. **Идемпотентность.** Create pair, join, daily done и завершение задач должны безопасно повторяться при двойном тапе и сетевом retry.
5. **Безопасность.** Закрыть setup, добавить rate limiting, security headers, строгий allowlist origin, constant-time сравнение секретов, короткоживущую сессию Mini App с понятным восстановлением.

## Что проверено и не является ошибкой

- HMAC-проверка Telegram `initData` реализована по спецификации; `signature` входит в check string, `hash` исключается (`worker.js:30-45`).
- Сравнение initData использует XOR по всей длине (`worker.js:41-44`); утечки по длине для 64-символьного hex нет.
- SQL-инъекций не найдено: все пользовательские значения идут через `.bind()`.
- IDOR в Worker не найден: мутации ограничены серверным `pair_id`.
- Активной XSS нет: пользовательские данные экранируются `esc()` (`public/app.js:13`).
- `cache-control: no-store` на JSON-ответах выставлен корректно (`worker.js:11-14`).
- Статика и Worker не конфликтуют: `/api/*` и webhook доходят до кода; `ASSETS` отдаёт файлы.
- `/health` возвращает только булевы значения, не раскрывая секреты.
- Схема миграции D1 и `ensureSchema` сейчас совпадают по таблицам и индексам.
- `INSERT OR IGNORE` в `dailyFor` и guard `done_by IS NULL` защищают от повторной отметки на уровне statement; проблема только в отдельной транзакции начисления XP.
- SQLite настроен разумно: WAL, `foreign_keys=ON`, `busy_timeout=5000`, единый коннект и lock.
- В текущих данных XSS через `empty()`/`field()` невозможен: аргументы — константы; это latent-риск, а не активная уязвимость.
- `hidden` корректно работает для `#app` и `#onboarding`; сломан только `.outside`.
- Редирект `/app.html → /app` не ломает Mini App сейчас, но создаёт лишний хоп.
- Код приглашения 8 hex (32 бита) практически не перебирается; отсутствие rate limit важнее длины.
- Ссылки `t.me` имеют `rel="noopener noreferrer"`.
- Лендинг адаптивен, горизонтального переполнения в обычном контенте не обнаружено.
