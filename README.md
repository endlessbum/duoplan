# DuoPlan

Telegram Mini App для пар: общие планы, значимые даты, дневник, вишлист и
«ритуал дня» с очками и сериями.

В репозитории две поверхности: production — Cloudflare Worker (`worker.js` + D1),
локальная — Python-бот (`duoplan/`, aiogram + SQLite).

- Лендинг — <https://duoplan.stacheight.workers.dev>
- Mini App — <https://duoplan.stacheight.workers.dev/app>
- Бот — [@duoplanbot](https://t.me/duoplanbot)
- Состояние сервиса — `GET /health` → `{ ok, service: "duoplan", version, database }`
- Текущая версия — `2026.11.11.50` (`APP_VERSION` и `DB_SCHEMA_VERSION` в `worker.js`)

## Возможности

| Раздел | Что умеет |
|---|---|
| Главная | Ритуал дня (одно совместное действие на пару в сутки, +10 XP каждому), серия дней, очки «Мои» и «Вместе», ближайшие планы и даты |
| Планы | Заголовок с разметкой, дата и время, повтор (`monthly` / `yearly`), приватность, завершение и возврат в работу |
| Даты | Значимые даты с временем, ежегодный (`recurs`) или ежемесячный повтор, приватные даты — видны только автору; сегмент «Дни рождения» (`kind='birthday'`, всегда ежегодные) с напоминанием за 3 дня |
| Места | Список «куда сходить», ссылка на карту, отметка посещения; кнопка «Рандом» тянет случайное непосещённое место из колоды — показ и подтверждение посещения разделены |
| Дневник | Записи с необязательным заголовком, разметка в тексте, догрузка архива страницами; сегмент «Цитаты» — фразы с автором или источником |
| Желания | Внутри «Нашей пары»: два списка «Мои / Его (Её)», ссылка на подарок, отметка «исполнено» с датой вручения |
| Наша пара | Переключатель «Профиль / Желания», календарь месяца, настройки (сводки, акцент, аватар, имя партнёра), PIN, часовой пояс, экспорт, выход |

Напоминания приходят от бота: утренняя сводка (в ней дни рождения — отдельным
абзацем), сводка о завтрашних датах, предупреждение о дне рождения за 3 дня и
напоминания о планах за 3 часа и за 1 час.

## Архитектура

| Путь | Назначение |
|---|---|
| `worker.js` | Production backend: API, Telegram webhook, cron-уведомления, `ensureSchema` |
| `wrangler.jsonc` | Worker, D1 binding, assets, cron, публичные vars |
| `migrations/` | 29 миграций схемы D1 |
| `public/` | Лендинг, Mini App (`app.html` + `app.js` + `app.css` + `nav.js`), setup, 404 |
| `duoplan/` | Локальный Python-бот: handlers, services, SQLite-схема, FSM, rich-text |
| `scripts/` | Бэкап D1, экспорт SQLite → D1, dev-стенд, проверка жеста касаниями, упаковка проекта |
| `tests/` | pytest (28 файлов) и `node:test` (64 файла) + браузерные harness'ы |

**Production:** Cloudflare Worker + D1 + static assets. Worker обслуживает только
`/api/*`, `/health` и `/telegram/*` (`run_worker_first`), остальное отдаёт
платформа ассетов из `public/`.

**Python-бот** — отдельная локальная поверхность. Он не должен работать
одновременно с Worker на одном `BOT_TOKEN`: webhook и long polling конфликтуют
(`409`). При старте бот проверяет `getWebhookInfo` и отказывается запускать
polling, если webhook уже установлен (код выхода `2`).

Схема общих таблиц задаётся только миграциями D1 и `ensureSchema` в `worker.js`;
`duoplan/db/schema.py` обязан совпадать с ними по составу колонок (расхождение
ловит `tests/test_schema_parity.py`). Ритуал дня считается одной и той же
функцией на обеих поверхностях — `dailyAction()` в `worker.js` и
`_daily_action()` в `duoplan/services.py`; паритет держат
`tests/test_daily_parity.*` на общих векторах из `tests/fixtures/daily_actions.json`.
Список колонок в `scripts/export_sqlite_to_d1.py` сверяется со схемой —
`tests/test_export.py::test_export_covers_every_column_of_current_schema`.

Файлы в `migrations/` — валидный SQL для SQLite: `ALTER TABLE ... ADD COLUMN
IF NOT EXISTS` там недопустим (такого синтаксиса нет), на чистой базе миграция
падает с ошибкой `near "EXISTS"`. Идемпотентность даёт не `IF NOT EXISTS`, а
однократное применение: применённую миграцию нельзя редактировать — её текст
уже записан в `d1_migrations`.

`ensureSchema()` в `worker.js` создаёт те же таблицы и догоняет недостающие
колонки по `PRAGMA table_info`; версия записывается в `app_meta.schema_version`.
Если она совпала с `DB_SCHEMA_VERSION`, DDL пропускается — поэтому версию схемы
поднимают при каждом изменении структуры, и она не может опережать текущую дату
(проверяет `tests/test_webhook_hardening.test.mjs`; на релизе `APP_VERSION` и
`DB_SCHEMA_VERSION` совпадают).

## Быстрый старт

### Worker + D1 локально

```bash
wrangler d1 migrations apply duoplan --local
wrangler dev --local --port 8788
```

Для локального dev создайте `.dev.vars` (он в `.gitignore`) с тестовыми
`BOT_TOKEN`, `WEBHOOK_SECRET`, `SETUP_TOKEN`, `APP_ORIGIN`.

Не запускайте `wrangler d1 migrations apply` на базе, уже инициализированной
через `/setup`: схема в production управляется Worker'ом.

### Python-бот

```bash
python -m venv .venv
.venv/Scripts/python.exe -m pip install -r requirements.txt
cp .env.example .env          # заполните BOT_TOKEN
.venv/Scripts/python.exe -m duoplan
```

### Демо без Telegram и D1

Директория `demo/` удалена из репозитория: витрина Mini App с фейковым API
больше не поддерживается. Для локальной разработки используйте
`scripts/dev-stand.mjs` — он поднимает Worker с D1 и Telegram-заглушкой.

## Cloudflare

`wrangler.jsonc` уже описывает Worker `duoplan`, D1 binding `DB`
(`database_id 6c5e8724-…`, `migrations_dir ./migrations`), ассеты из `./public`
с `not_found_handling: 404-page`, cron `*/15 * * * *` и observability.

Публичные переменные (`vars`):

| Имя | Назначение |
|---|---|
| `APP_ORIGIN` | Origin приложения: ссылки бота, `setWebhook`, проверка `Origin` в `/api/setup` |
| `BOT_USERNAME` | Username бота без `@` для ссылок `t.me/...` |
| `BOT_NAME` | Необязательное имя бота в текстах (по умолчанию `DuoPlan`) |
| `OWNER_IDS` | Telegram-ID владельца(ов) через запятую — гейт приватного бота (см. ниже); пустой — бот открыт |

В `wrangler.jsonc` заданы `APP_ORIGIN`, `BOT_USERNAME` и `OWNER_IDS`; `BOT_NAME`
можно добавить, если нужно другое имя в сообщениях.

Секреты Worker:

| Имя | Назначение |
|---|---|
| `BOT_TOKEN` | Токен @BotFather |
| `WEBHOOK_SECRET` | Случайная строка для проверки Telegram webhook (`x-telegram-bot-api-secret-token`) |
| `SETUP_TOKEN` | Необязательный отдельный секрет для `/api/setup` (иначе используется `BOT_TOKEN`) |
| `OMDB_API_KEY` | Ключ [OMDb API](https://www.omdbapi.com/apikey.aspx) (бесплатный, 1000/день) — основной источник карточки фильма: рейтинг, жанр, длительность. Без него карточка собирается с suggest-эндпоинта IMDb без рейтинга (пилюля «IMDb —»); поиск подсказок всегда идёт по IMDb suggest — поиск OMDb слаб на русских и частичных запросах |
| `TMDB_API_KEY` | Ключ [TMDB](https://www.themoviedb.org/settings/api) (бесплатный) — русские названия подсказок и карточек «Кино» (локализация ru-RU по tt-id) и оценка-фолбэк, когда у IMDb ещё нет голосов (пилюля «TMDB 7.5» вместо «IMDb —»). Без него названия остаются английскими; поиск и добавление работают в любом случае |

Активация:

1. Задайте секреты в **Workers & Pages → duoplan → Settings → Variables and Secrets**.
2. Откройте `/setup` (или `/setup.html`), введите `SETUP_TOKEN` либо `BOT_TOKEN`.
3. Страница создаст/обновит таблицы D1, установит webhook, команды бота и
   меню-кнопку Mini App.

`POST /api/setup` ограничен 5 попытками за 10 минут на IP (лимит применяется до
проверки секрета), сверяет `Origin` с `APP_ORIGIN` и возвращает
`{ ok, webhook_url, mini_app_url, has_main_web_app, version }`.

### Приватный бот (`OWNER_IDS`)

Если `OWNER_IDS` задан, бот работает по приглашениям — и в Worker, и в Python-боте:

- владелец из списка получает полный доступ;
- уже зарегистрированный пользователь (есть строка в `users`) — полный доступ:
  он когда-то вошёл по ссылке-приглашению;
- незнакомец может только открыть `/start <КОД>` с кодом открытой пары
  (`t.me/<бот>?start=КОД`) — до подтверждения кода он не создаётся в `users`;
- остальным бот отвечает, что доступ по приглашению.

В Worker гейт стоит в `api()` и `webhook()` до `ensureUser()`, в Python-боте —
`PrivateBotMiddleware` (outer, до `EnsureUserMiddleware`). Пустой `OWNER_IDS`
возвращает прежнее открытое поведение.

### Кэш статики Mini App

`/app.js`, `/app.css`, `/nav.js` и `/zoom-guard.js` отдаются через Cloudflare
assets; в `public/_headers` им выставлен
`Cache-Control: public, max-age=31536000, immutable`. HTML-страницы, `/` и `/app`
помечены `no-cache`, setup-ассеты тоже (они не версионируются).

Чтобы деплой не оставлял пользователей на старом скрипте, все четыре ассета
подключаются с query-string: `/app.js?v=<APP_VERSION>` (значение берётся из
`const APP_VERSION` в `worker.js` и дублируется в `public/app.html`). Новый
деплой → новый URL → новый cache entry; HTML не кэшируется, поэтому свежая
версия подхватывается сразу.

Дополнительно `tests/test_headers_cache.test.mjs` сверяет sha256 каждого ассета
с манифестом `tests/asset-hashes.json`: правка содержимого без обновления
манифеста валит прогон (манифест тест перезаписывает сам — его коммитят вместе
с новой версией), а сам манифест проверяет, что `?v=` в `app.html` совпадает
с `APP_VERSION`.

В `public/_headers` также заданы `X-Content-Type-Options: nosniff`,
`Referrer-Policy: no-referrer`, `Permissions-Policy` и CSP с `frame-ancestors`
для `web.telegram.org`.

### Резервные копии D1

Экспорт данных из настроек пары (один текстовый файл `Экспорт.txt`,
отправляемый документом `text/plain` — выбранные разделы: планы, кино,
значимые даты, дни рождения, места, поездки, записи дневника, цитаты,
желания; для каждой — свой состав выгрузки) не заменяет резервное
копирование базы: настройки и очки в файлы не попадают.
Вся база выгружается скриптом:

```bash
bash scripts/backup-d1.sh   # дамп в backups/duoplan-<дата>-<время>.sql
```

- **Периодичность:** запуск вручную или по расписанию на машине с wrangler —
  минимум раз в неделю; перед любым импортом (`export_sqlite_to_d1.py`) — обязательно.
- **Хранение:** дамп содержит все личные записи пар — храните его вне
  репозитория и шифруйте при выкладке в облако. `backups/` уже в `.gitignore`.
- **Восстановление:** только в отдельную базу — `npx wrangler d1 create
  duoplan-restore`, затем `npx wrangler d1 execute duoplan-restore --remote
  --file=<дамп.sql>`. Периодически проверяйте, что копия восстанавливается
  и содержит свежие записи.
- **Точечный откат:** у D1 есть Time Travel (восстановление состояния на
  момент времени, срок хранения зависит от тарифа): `npx wrangler d1
  time-travel duoplan --restore-to="<ISO-время>"`. Это страховка от
  случайного DELETE, но не замена дампам — срок хранения ограничен.

### Перенос локальных данных в production

```bash
.venv/Scripts/python.exe scripts/export_sqlite_to_d1.py
wrangler d1 execute duoplan --remote --file data/duoplan-d1-import.sql
```

Перед импортом сделайте резервную копию D1: скрипт использует `INSERT OR REPLACE`.
Импорт предназначен для пустой или подготовленной целевой D1: при совпадении ID
существующие записи могут быть заменены каскадно. Для объединения с работающей
базой сначала проверьте конфликты ID.

Колонка вне списка в `export_sqlite_to_d1.py` молча теряется при импорте:
для `is_private` это тихая смена приватности (личный план становится общим),
для `wishes.done_at`/`wishes.url` — потеря звезды календаря и ссылки, для
`photo_url`/`show_avatar`/`partner_custom_name` — аватаров и личного имени.
Поэтому после изменения схемы список колонок обновляется в том же коммите.

## API

Все `/api/*`, кроме `setup`, требуют заголовок `x-telegram-init-data` с подписанным
Telegram `initData`; необязательный `x-timezone` задаёт локальный день при
создании пользователя. Ошибки возвращаются как `{ error, code, requestId }`.

| Метод и путь | Назначение |
|---|---|
| `GET /api/state` | Всё состояние: пользователь, пара, активные планы/даты/желания, цитаты, места, последние записи, ритуал |
| `POST /api/pair/create` | Создать пространство (код приглашения — 8 hex-символов) |
| `POST /api/pair/join` | Войти по коду `{ code }` |
| `POST /api/pair/leave` | Выйти из пространства (владелец передаёт его партнёру). После выхода у оставшегося контент заморожен: мутации отвечают `403 PARTNER_ABSENT`, пока партнёр не вернётся по коду; чтение и личное (настройки, часовой пояс, экспорт, выход) работают. Партнёр, вернувшийся по тому же коду, уведомляет оставшегося; код пары, закрывшейся полным выходом, попадает в `closed_codes` — вход по нему отвечает `410 PAIR_CLOSED` (в лимит перебора пишется, как и `404`) |
| `POST /api/pair/timezone` | Общий часовой пояс пары `{ timezone }` |
| `POST /api/gender` | Пол `{ gender: "male" \| "female" }`, доступно до онбординга |
| `POST /api/settings` | `accent_color`, `digest_time`, `digest_enabled`, `dates_digest_time`, `dates_digest_enabled`, `show_avatar`, `partner_name` |
| `GET /api/archive` | Страница архива: `type=memories\|done_tasks\|wishes\|done_wishes`, `page` (по 20, не дальше 500) |
| `POST /api/data/export` | Выслать в чат «Экспорт.txt» с выбранными разделами |
| `POST /api/tasks` | План `{ title, day, time, monthly, yearly, is_private }` |
| `POST /api/dates` | Дата `{ title, day, time, recurs, monthly, is_private, kind }`: `kind='birthday'` — день рождения (всегда ежегодный, без времени и ежемесячного повтора) |
| `POST /api/memories` | Запись дневника `{ title, body }` (день ставится по часовому поясу пары) |
| `POST /api/wishes` | Желание `{ body, url }` |
| `POST /api/quotes` | Цитата `{ body, source }` — источник необязателен |
| `POST /api/places` | Место `{ title, note, url }` |
| `POST /api/places/:id/visited\|unvisited` | Отметить посещение (пишет `visited_by`/`visited_at`) или вернуть в список |
| `POST /api/movies` | Фильм по `{ imdb_id }`: карточка собирается из OMDb/IMDb suggest, название и жанр локализует TMDB |
| `GET /api/movies/:id/details` | Описание, все жанры, главные актёры, режиссёр/создатели, премьера и рейтинги RT/Metacritic (TMDB ru + OMDb, кешируется в `movies.details`) |
| `POST /api/movies/:id/watched` | «Просмотрено» с обязательной оценкой `{ rating: 1…10 }`; без целой оценки 1–10 — 400, карточка не переходит в «Просмотренные» |
| `POST /api/movies/:id/rate` | Оценка второго партнёра `{ rating: 1…10 }` (только для просмотренного); RAofP — среднее обоих голосов |
| `POST /api/movies/:id/unwatched` | Вернуть в «Хотим посмотреть»; оценки пары сбрасываются |
| `POST /api/daily/done` | Отметить ритуал дня (+10 XP, идемпотентно) |
| `PATCH /api/{tasks\|dates\|memories\|wishes\|quotes\|places}/:id` | Изменить запись |
| `DELETE /api/{tasks\|dates\|memories\|wishes\|quotes\|places\|movies}/:id` | Удалить запись |
| `POST /api/tasks/:id/done\|reopen` | Завершить или вернуть план |
| `POST /api/wishes/:id/done\|reopen` | Отметить желание исполненным (только своё) |
| `POST /api/setup` | Активация: схема, webhook, команды, меню-кнопка |
| `GET /health` | Проверка Worker и доступности D1 |
| `POST /telegram/webhook` | Telegram webhook (проверка `WEBHOOK_SECRET`) |

Лимиты запросов (`rate_limits`; окна фиксированные — ключ включает номер окна,
поэтому счётчик начинается заново на его границе):

| Ключ | Лимит |
|---|---|
| `u:<tg_id>` | 240 запросов в минуту |
| `export:<tg_id>` | 5 экспортов в час |
| `setup:<ip>` | 5 попыток за 10 минут |
| `jf:<tg_id>:<окно>` | 5 неудачных кодов за 15 минут — дальше вход по коду блокируется |

Лимит пользователя проверяется **до** записи в `users`, поэтому флуд не создаёт
строк. Попытки входа считаются отдельно и только неудачные: успешный код
счётчик не тратит, а каждый неудачный (`CODE_NOT_FOUND`) приближает блокировку
на 15 минут.

`/api/state` отдаёт до 200 активных записей и 10 последних записей архивов
(`STATE_ACTIVE_LIMIT` / `STATE_RECENT_LIMIT`); остальное клиент догружает
страницами через `/api/archive`. Догрузка есть у планов, дат, желаний и
дневника (плюс архивы завершённых планов и вручённых желаний). У цитат, мест,
кино и копилок архива нет: они ограничены теми же 200 записями — для пары это
заведомо больше реальных объёмов, но при переполнении «хвост» в интерфейс не
попадёт.

## Напоминания в боте (cron)

`wrangler.jsonc` задаёт 15-минутный cron (`triggers.crons`): `sendDigests()` в
`worker.js` обходит пары и отправляет каждому партнёру личные сообщения от бота
с кнопкой Mini App.

- **Утренняя сводка** — планы и значимые даты на сегодня и завтра, двумя
  абзацами («Значимые даты» / «Планы»). Время настраивается на вкладке
  «Наша пара» → «Настройки» (персональное, по умолчанию 09:00, можно выключить).
- **Сводка о датах за сутки** — завтрашние даты накануне в выбранное время
  (отдельная настройка, тоже персональная и отключаемая).
- **День рождения за 3 дня** — отдельное сообщение (`birthday3d:<id>`), чтобы
  успеть выбрать подарок. В утренней сводке дни рождения идут отдельным
  абзацем и не маскируются спойлером даже при `is_private`: сообщение уходит
  только автору, а «Скрытый» в строке «день рождения у Скрытый» бесполезен.
- **Напоминания о планах** — если у плана указано время, бот предупреждает
  за 3 часа и за 1 час (всегда включены, дедуп по `task3h:<id>`/`task1h:<id>`).
  Окна не пересекаются: до события меньше часа приходит только «Через час» —
  раньше приходили оба сообщения, и «Через 3 часа» врало про событие через
  20 минут (`planTaskReminders` в `worker.js`).
- Дедупликация — таблица `notification_log` (ключ `tg_id, day, kind`), хвост
  старше недели чистится на каждом тике; сбой доставки (кроме постоянных
  ошибок вроде заблокированного бота) повторится на следующем тике.
- Очередь тика — устойчивый курсор `app_meta.notification_cursor`: каждый тик
  берёт следующие `DIGEST_MAX_PAIRS = 10` пар по возрастанию `id`, хвост
  исчерпан — с начала. Так каждая пара обходится за `ceil(N / 10)` тиков, и
  разница числа посещений за любое окно не больше 1 (раньше была ротация «по
  минутам суток», которая голодала при росте числа пар).
- Бюджет подзапросов Free-плана (50 на вызов) считается явно: 3 запроса на пару
  и 2 на каждую отправку, порог `DIGEST_BUDGET = 44`; не успевшие пары догоняют
  на следующих тиках.
- Личные даты (`dates.is_private=1`) попадают в сводки только их автору
  (`created_by`), из выдачи партнёру они убираются ещё в SQL `state()/archive`.
- Личные планы (`tasks.is_private=1`) — зеркально датам: партнёр не видит их
  ни в списках, ни в напоминаниях; по прямому `id` API отвечает 404, чтобы не
  раскрывать факт существования записи. Автору заголовок приходит под
  спойлером «Скрытый» (`<tg-spoiler>`), чтобы план-сюрприз не читался с экрана
  блокировки. Списки в самом боте (`DuoPlanService.tasks/dates` с `viewer_id`)
  фильтруют чужие личные записи так же.
- Часовой пояс — `pairs.timezone`.

## Интерфейс

### Нижняя навигация (Liquid Glass)

Панель и «жидкая» капля живут в `public/nav.js` (фабрика `createLiquidNav`),
разметка — в `public/app.html`, материал — в `public/app.css`, связь с
остальным приложением — в `public/app.js` (`updateDroplet` → `setActive`).
Пять вкладок: «Главная», «Планы», «Даты», «Места», «Дневник»; «Наша пара»
открывается кнопкой-пилюлей с аватарами вверху справа и содержит переключатель
«Профиль / Желания». Ещё два вида живут сегментами внутри вкладок: «Наши / Дни
рождения» в «Датах» и «Записи / Цитаты» в «Дневнике». Восемь отдельных вкладок
в док не помещаются: на 360 px слот при восьми вкладках — 40 px, а подпись
«Желания» занимает около 38 px; линза капли вдобавок расширяет вкладку на
6–16%. Поэтому новые разделы разложены по родственным экранам, а не добавлены
в бар.

- **Материал.** Полупрозрачный фон `--nav-glass-bg`, размытие и насыщение
  (`backdrop-filter: blur(34px) saturate(175%)`), верхний блик `--glass-sheen`,
  внутренняя окантовка `::after` (`--glass-inner`), мягкая тень. Значения
  свои для светлой и тёмной темы.
- **Капля.** Это SVG-путь, а не `scaleX/scaleY`: контур пересчитывается по
  скорости и направлению — передний край вытягивается (до 28% ширины), задний
  поджимается (18%), высота проседает (26%), центр смещается на 10%. В покое
  капля «собрана»: `REST_NARROW = 0.92`, то есть уже слота, и растягивается
  до полной ширины только в движении — это и читается как вода. У края панели
  форма сдвигается внутрь, а не сплющивается. Пружина возврата намеренно
  недодемпфирована (`ζ ≈ 0.48`): после отпускания капля приезжает с перелётом
  и пару раз качается. Градиент капли — от `--droplet-hi` через
  `--droplet-fill` к `--droplet-deep`, тень — `--droplet-halo`; все они
  пересчитываются в `applyAccent()` из палитры. Панель прижата к низу:
  `bottom = safe-area + 8px`.
- **Статичный док.** В панели меняется **только цвет**: у вкладки нет
  `:active`-масштаба, у иконки — трансформаций, у активной подписи —
  изменения начертания (иначе текст «прыгал» бы по ширине), а
  `-webkit-tap-highlight-color: transparent` убирает вспышку при касании.
  Геометрия вкладки неизменна всегда — на этом же держится и расчёт площади
  под каплей: `getBoundingClientRect()` возвращает несжатые прямоугольники.
- **Линза капли.** Копии контента нет: вкладка под каплей увеличивается
  трансформацией самой кнопки — 6% в покое, до 16% на скорости, наклон
  `rotateY` до 10° зависит от её положения относительно центра капли, поэтому
  у краёв поджимается перспектива. В покое наклона нет и `perspective()` не
  применяется — иначе слой растрируется в 1× и иконка мылится. Перед замером
  рамок трансформация снимается, иначе `getBoundingClientRect()` вернул бы
  увеличенный прямоугольник и сбил расчёт накрытия. Копия контента с SVG-маской
  была убрана: в WebView, где маска на HTML-элементе не применяется, слой не
  обрезался и красил акцентом всю панель.
- **Перекраска.** Акцент получает только та вкладка, которую капля накрыла
  сильнее всех (`leader`), и ровно настолько, насколько накрыла
  (`coverageOf` → `mixColor(--muted, --berry, ratio)`). Остальные всегда
  обычного цвета, поэтому «двух активных» не бывает. Цвета читаются из
  CSS-переменных и перечитываются в `refresh()` — app.js дёргает его после
  смены темы и акцентной палитры.
- **Переключатели в странице.** Та же капля используется не только в доке:
  `createLiquidNav({ nav, items })` собирает SVG сам, если её не передали
  (свой градиент, чтобы не зависеть от разметки панели), ищет цель по
  `data-tab` и берёт цвета из `idleVar`/`accentVar`. Так подключены
  «Профиль / Желания» в «Нашей паре», «Наши / Дни рождения» в «Датах»,
  «Записи / Цитаты» в «Дневнике» (`.seg-switch`) и «Мои / Его» в желаниях
  (`.wish-switch`). Разметка вкладки перерисовывается целиком, поэтому
  `render()` снимает экземпляры в начале и монтирует новые в конце, а вид
  запоминается — капля приезжает с прежнего места, а не появляется сразу на
  новом. Само переключение вида меняет только тело (`#tab-body`/`#pair-body`),
  поэтому капля доезжает пружиной, как в главном баре.
- **Жест.** Захват начинается на активной вкладке (капля лежит под ней),
  порог 6 px отделяет тап от перетаскивания. Дальше `setPointerCapture` на
  панели: `pointermove` приходит даже когда палец вышел за её пределы, а
  вертикаль игнорируется — капля едет только по горизонтальной дорожке.
  `pointercancel`, `lostpointercapture` и `blur` откатывают жест без
  переключения; синтетический `click` после drag гасится один раз.
- **Выбор вкладки.** При отпускании контур капли сэмплируется
  (`getPointAtLength` + `getScreenCTM`), пересечение с каждой вкладкой
  считается клиппингом полигона (Sutherland–Hodgman) и площадью по формуле
  шнурков. Знаменатель — **полная площадь капли** (`coverageRatios`), а не
  сумма пересечений: иначе часть капли, лежащая вне кнопок, завышала бы долю
  до 100%. Нужно строго больше 50% с допуском 0.2% против численной
  погрешности; при 50/50 или «размазано» остаётся последняя однозначная цель.
  Пока палец не отпущен, страница не переключается — вкладка только
  подкрашивается по доле накрытия.
- **Защита от двойного click.** После успешного drag запоминается одноразовая
  запись `{pointerId, x, y, time}`; capture-обработчик гасит только click,
  совпавший по указателю, координатам (±14 px) и времени (700 мс). Отмена
  жеста (`pointercancel`, `lostpointercapture`) защиту не ставит, клавиатурные
  клики (`detail === 0`) не подавляются, а новый `pointerdown` сбрасывает
  запись.
- **WebView-фолбэк.** На части WebView (старый WKWebView, Android WebView)
  `touch-action` не отключает прокрутку: браузер начинал пан и уводил pointer
  в `pointercancel`, из-за чего жест обрывался на первом движении. Поэтому
  `touch-action: none` продублирован на самой вкладке (`.nav-item` — правило
  родителя не наследуется, а `auto` на child перебивает `pan-y` панели), а
  пока жив жест, `touchmove` отменяется (`{ passive: false }`). Цель жеста
  ищется обходом предков, а не `closest()`: на SVG-капле часть WebView не
  поднимается до `<button>`, и тап по капле не находил активную вкладку.
- **Потеря захвата у дочернего элемента.** Палец попадает не в `<button>`, а
  в иконку внутри него, поэтому браузер ставит неявный pointer capture на
  иконку. Наш `setPointerCapture(nav)` его снимает, и `lostpointercapture`
  всплывает до панели. Событие с `target !== nav` игнорируется: настоящая
  потеря захвата приходит на саму панель вместе с `pointercancel`.

Проверки: `tests/test_nav_geometry.test.mjs` (геометрия и правило 50%),
`tests/test_nav_shape.test.mjs` (контур и деформация),
`tests/test_nav_touch_guard.test.mjs` (фолбэк в WebView),
`tests/test_nav_lens.test.mjs` (линза и перекраска), `tests/nav-harness.html`

Нужен Node 22+ и Chrome (`--chrome <путь>` или `CHROME`).

### Масштаб интерфейса

Pinch-to-zoom в Mini App отключён на трёх уровнях, чтобы не зависеть от
поведения конкретного WebView:

- **viewport** в `public/app.html`: `maximum-scale=1, user-scalable=no`
  (плюс прежние `width=device-width`, `initial-scale=1`, `viewport-fit=cover`);
- **CSS**: `html { touch-action: pan-x pan-y }` — прокрутка одним пальцем
  разрешена в обе стороны, pinch-zoom и double-tap-zoom выключены. Панель
  навигации и её вкладки задают `touch-action: none`: панель не прокручивается,
  а жест капли перехватывает код (см. «Нижняя навигация»);
- **`public/zoom-guard.js`**: отменяет `touchstart`/`touchmove` при двух и
  более касаниях (одиночные не трогает), Safari-события `gesturestart`,
  `gesturechange`, `gestureend` и `Ctrl+wheel`; все слушатели с
  `{ passive: false }`.

`index.html`, `setup.html` и `404.html` — самостоятельные страницы вне
Telegram WebView, там масштабирование оставлено (доступность).

Проверка: `tests/test_zoom_guard.test.mjs` (обработчики, viewport, CSS) и
`tests/zoom-harness.html` (реальные TouchEvent, computed styles, drag капли
при включённой защите).

### Фон при прокрутке

Длинный свайп на iOS давал полосы другого цвета у верхней и нижней границы:
при отскоке (rubber-band) обнажается фон **WebView**, а туда уходил ключ
`bg_color` — цвет темы Telegram (в тёмной теме чёрный), а не фон приложения
`#161514`.

- `applyTheme()` читает `--bg` через `themeBackground()` и передаёт
  фактический hex в `tg.setBackgroundColor()` и `tg.setHeaderColor()`; тем же
  значением обновляется `<meta name="theme-color">`. Ключ `bg_color` остался
  только запасным вариантом, если `--bg` не hex.
- `html`/`body` красятся `var(--bg)`; `body` имеет `min-height: 100dvh`,
  поэтому при коротком содержимом под ним не остаётся незакрашенной области.
  `overscroll-behavior-y` не блокируется — нативный rubber-band на iOS остаётся
  плавным, так как фон WebView уже совпадает с `--bg`.

Проверка: `tests/test_scroll_theme.test.mjs`.

### Тема и акцент

Тема — «как в системе» / светлая / тёмная (`localStorage: duoplan.theme`).
Акцент — персональный: `users.accent_color` из набора
`berry | sage | ocean | violet | amber`, палитры под обе темы лежат в
`ACCENT_PALETTES` (`public/app.js`). Цвет применяется через `applyAccent()`:
пересчитываются `--berry*`, градиенты капли и цвета аватаров; акцент партнёра
приходит в `pair.partner_accent` и красит его аватар.

### Аватары и имя партнёра

- Фото профиля приходит из `initData` (`user.photo_url`) — `ensureUser()`
  сохраняет его при каждом открытии приложения, `state()` отдаёт
  `pair.photo1` (владелец) и `pair.photo2` (партнёр).
- Переключатель «Отображение аватара» (`users.show_avatar`) выбирает фото или
  букву; оба аватара рисуются в кнопке-пилюле вверху, которая открывает
  «Нашу пару» (`paintAvatarSlot` в `syncTopControls`).
- `users.partner_custom_name` — как владелец строки видит имя **партнёра**.
  Подставляется только в выдачу просматривающего: в имя пары и в подписи
  авторов воспоминаний/желаний. Партнёр этого имени не видит.

### Календарь на вкладке «Наша пара»

Карточка календаря стоит между участниками пространства и настройками
(`renderPairCalendar()` в `public/app.js`). Сетка месяца с понедельника, точки
событий и раскрывающийся список выбранного дня.

- **Данные.** Планы — `mergedArchive("tasks", appState.tasks)` (только открытые,
  только с заполненным `day`); значимые даты — `mergedArchive("dates", …)`;
  вручённые желания — `mergedArchive("done_wishes", appState.completedWishes)`.
  Завершённые планы и планы без даты в календарь не попадают.
- **Маркеры.** Зелёный — план, красный — значимая дата (`--cal-task`,
  `--cal-date`), жёлтая звезда — вручённое желание (`--cal-wish`), серый —
  личная запись (`--cal-private`). По одному маркеру на тип, цвета
  семантические и не зависят от акцентной палитры.
- **Вручённые желания.** Звезда ставится в день, когда желание отметили
  исполненным (`wishes.done_at`, миграция `0010`). Показываются только свои:
  `owner_id` сверяется с `appState.user.tg_id`. У записей, закрытых до
  появления колонки, даты вручения нет — звезды у них не будет.
- **Повторы.** Даты с `recurs` и планы с `yearly` проецируются на тот же месяц
  и день каждого года, начиная с года создания; 29 февраля показывается только
  в високосные годы (проверка через `calendarDaysInMonth`, без переноса на
  28-е/1-е). `monthly` (у планов и дат) ставит запись на тот же день каждого
  месяца, если такой день в месяце существует.
- **Приватность.** Календарь не делает собственных запросов: он использует
  `state` и `/api/archive`, где фильтр `(is_private=0 OR created_by=?)` стоит
  в SQL. Личные записи партнёра в календарь не попадают.
- **Догрузка.** `/api/state` отдаёт до 200 активных записей (и 10 последних
  вручённых желаний); если лимит достигнут, `ensureCalendarArchive()` в фоне
  листает `/api/archive` до `hasMore: false`, дедуп по `id`, без блокировки
  первого рендера.
- **Навигация.** Месяц и выбранный день живут в модуле (`calendarMonth`,
  `calendarSelected`), поэтому обычный refresh не сбрасывает их.

Проверка: `tests/test_calendar.test.mjs`.

### Разметка текста (Telegram-стиль)

Заголовки планов и дат, воспоминания и желания хранят разметку прямо в тексте
теми же маркерами, что и Telegram: `**жирный**`, `_курсив_`, `__подчёркнутый__`,
`~~зачёркнутый~~`, `||спойлер||`, строки с префиксом `> ` — цитата.

- В Mini App при выделении текста в поле появляется плавающее меню
  (жирный/курсив/подчёркнутый/зачёркнутый/спойлер/цитата); повторное нажатие
  снимает маркер. Рендер — `renderRichText()` в `public/app.js`: текст
  экранируется до наклейки тегов из фиксированного набора, произвольный HTML
  из поля не проходит. Спойлер раскрывается тапом, цитата красится в
  акцентный цвет пользователя (`--berry*`).
- В уведомлениях бота ту же разметку разворачивает `richToHtml()` в
  `worker.js` (HTML-поднабор Telegram: `<b>`, `<i>`, `<u>`, `<s>`,
  `<tg-spoiler>`, `<blockquote>`); незакрытые маркеры закрываются
  автоматически, чтобы `sendMessage` не вернул 400.
- Списки в самом боте (aiogram) рендерит порт `richToHtml` —
  `duoplan/richtext.py`: `rich_to_html()` собирает HTML, `rich_to_plain()`
  снимает разметку для подписей inline-кнопок (кнопки `parse_mode` не
  поддерживают). `safe_edit(..., html=True)` передаёт `parse_mode="HTML"`
  только этим сообщениям, остальные тексты остаются plain-текстом, поэтому
  «<» в служебных сообщениях и ошибках ничего не ломает.
- Каждый пункт списка рендерится отдельным блоком (`handlers.rich_list_item`):
  номер, дата и автор приписываются снаружи, а разметка заголовка — внутри,
  поэтому цитата с первой строки становится `<blockquote>`, а не текстом «> ».

### Ссылка у желания

- У желания есть опциональная ссылка (`wishes.url`), которую пользователь
  указывает при создании («что именно он хочет» — подарок, билет и т.п.).
- В карточке желания ссылка не выводится текстом: вместо неё кнопка «Ссылка»,
  при тапе пользователь открывает указанную ссылку. Кнопка есть и у исполненных
  желаний.
- При редактировании карточки ссылка подставляется в поле ввода и сохраняется
  через `PATCH /api/wishes/:id` — тем же UPDATE, что и текст, чтобы при
  некорректном URL не оставалось полуприменённой правки.

### Выход из пространства

- Пока партнёр не присоединился (`pairs.user_b=0`), на вкладке «Наша пара»
  показывается карточка «Приглашение партнёра» с кодом и ссылкой. После входа
  партнёра (`user_b` заполнен) карточка скрывается; `state()` при этом не
  отдаёт код, чтобы им нельзя было поделиться из готовой пары.
- Если партнёр выходит (`POST /api/pair/leave`), сервер обнуляет `user_b`
  (а когда уходит владелец — передаёт пространство партнёру и делает его
  владельцем). У оставшегося карточка приглашения появляется снова: `state()`
  возвращает прежний код пары, и по нему можно позвать партнёра ещё раз.
- Оставшийся партнёр получает сообщение от бота: «<имя> больше не в вашем
  пространстве» с кнопкой Mini App. Выход фиксируется в БД до отправки, поэтому
  сбой Telegram не отменяет само действие.

## Ограничения и модель безопасности

Что защита даёт, а что нет — описано как есть:

- **Сессия `initData`.** Telegram подписывает `initData` при каждом запуске
  Mini App и не обновляет его в открытом приложении, поэтому Worker принимает
  подпись возрастом до 7 дней (`MAX_AGE` в `telegramUser()`). Украденный
  `initData` остаётся рабочим в этом окне; компромисс осознанный — более
  короткий порог обрывал живую сессию на второй день. Обмена на собственные
  серверные сессии нет.
- **PIN на вход.** Четырёхзначный пароль хранится в `localStorage` и блокирует
  только интерфейс на этом устройстве. Это не шифрование и не серверная
  авторизация: данные доступны любому с валидной сессией Telegram.
- **Приватный бот.** `OWNER_IDS` закрывает доступ посторонним, но не заменяет
  авторизацию: приглашённый по коду остаётся в `users` навсегда.
- **Лимиты.** 240 запросов в минуту на аккаунт, 5 экспортов в час, 5 попыток
  входа по коду за 15 минут, 5 вызовов `/api/setup` за 10 минут на IP.
  Перебор кода приглашения (8 hex-символов) ограничен именно счётчиком
  неудачных попыток.
- **Уведомления.** Cron раз в 15 минут с бюджетом D1-запросов на прогон:
  сводки и напоминания приходят с задержкой до одного тика, при очереди пар —
  дольше. Это не realtime-доставка.
- **Хранение.** Записи дневника, планы и даты лежат в D1 открытым текстом;
  конфиденциальность держится на защите аккаунта Cloudflare. Сквозного
  шифрования нет.
- **Экспорт данных.** Кнопка «Экспортировать» на вкладке «Наша пара»
  открывает выбор разделов: планы (все или личные), кино (не просмотренные),
  значимые даты (все или личные), дни рождения (все или личные), места,
  записи дневника, цитаты и желания (все или только свои), поездки (все или
  только свои). Бот присылает один текстовый файл `Экспорт.txt` с выбранным;
  личные записи партнёра не попадают
  в выгрузку ни в каком составе. Полная копия базы —
  `scripts/backup-d1.sh` (см. «Резервные копии D1»).

## Python-бот

```bash
python -m venv .venv
.venv/Scripts/python.exe -m pip install -r requirements.txt
cp .env.example .env          # заполните BOT_TOKEN
.venv/Scripts/python.exe -m duoplan
```

Переменные: `BOT_TOKEN`, `BOT_USERNAME`, `DB_PATH`, `TZ`, `BOT_NAME`, `FSM_TTL`,
`ADMIN_CHAT_ID`, `OWNER_IDS` (см. `.env.example`). Секреты хранятся только в
`.env`, он в `.gitignore`.

- База по умолчанию — `data/duoplan.db`. Версия схемы хранится в
  `PRAGMA user_version` (сейчас `7`), миграции идемпотентны и не удаляют данные.
  Старые базы, где версия лежала в `meta.schema_version`, читаются и переводятся
  на новую дисциплину.
- FSM-состояния хранятся в SQLite (`fsm_states`) с TTL (по умолчанию 7 дней,
  `FSM_TTL=0` — без ограничения) и чистятся при старте.
- Команды: `/start` (в том числе `/start <КОД>` — вход по приглашению),
  `/menu`, `/help`, `/cancel`. Остальное — кнопки и пошаговые формы.
- Очки и уровни: `duoplan/game/levels.py` — порог следующего уровня
  `100 * level²` (100 XP — второй, 400 XP — третий), восемь званий
  («Искры», «Тёплый свет», … «Штиль»), выше таблицы звания идут по кругу.
- Часовой пояс у бота один — `TZ` из `.env` (по умолчанию `Europe/Moscow`).
  Колонку `pairs.timezone`, которую выставляет Mini App, бот не читает: «сегодня»
  ритуала, день записей дневника и сортировки планов считаются по `TZ`. Бот и
  Worker не могут работать одновременно на одном `BOT_TOKEN` (polling vs
  webhook), так что расхождение проявляется только если `TZ` отличается от
  пояса, выставленного паре через Mini App.
- Ошибки обработки уходят в `ADMIN_CHAT_ID`, если он задан.

## Версия

Версия Python-пакета — `duoplan/__init__.py` (`__version__ = "1.0.0"`);
`pyproject.toml` читает её через `dynamic = ["version"]`, точка входа —
`duoplan = duoplan.__main__:run`. Версия Worker — `APP_VERSION` в `worker.js`
(`2026.11.11.50`), она же подставляется в `?v=` у ассетов и должна совпадать с
`DB_SCHEMA_VERSION` на релизе.
